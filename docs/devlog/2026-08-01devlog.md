### 19:57 - Phase 0 Steps 0.1-0.6: project skeleton, pinned deps, governance docs, public repo

I started a new one today. vanlife-dashboard, a native desktop app to help me sort raw vanlife documentary footage before it ever gets near DaVinci Resolve. This one's a little different from the main SEEKERS_GHOSTS build because it lives in its own public repo, its own venv, and it's meant to actually get used on real footage, not just prove out an architecture.

First thing I did was lay out the skeleton under `_test_project\vanlife-dashboard\`, app folder, ui subfolder, data folder with a proxies cache, docs with a devlog folder. Then `python -m venv .venv` right at the project root. I wanted this one fully isolated from whatever's floating around on system Python, and honestly it felt good to start clean instead of inheriting a pile of packages I didn't ask for.

Before I touched requirements.txt I actually went and checked PyPI live for every package I was about to pin. PySide6 6.11.1, python-dotenv 1.2.2, PyYAML 6.0.3, faster-whisper 1.2.1, and then psutil and nvidia-ml-py for a resource watchdog I'm planning a few phases out. Pinned every one of them exact, no loose `>=` floors. Installed clean into the venv, ran pip freeze after to confirm every version matched what I pinned. PySide6's addons package alone was almost 170MB, that download took a minute, but everything landed where it should.

The part that took more thought than I expected was the git situation. This project sits physically inside the SEEKERS_GHOSTS working tree, but it needed to be its own independent repo, public, separate history, separate everything. That means SEEKERS_GHOSTS's own gitignore had to learn to ignore its own subfolder, which is a weird thing to stare at for a second before it clicks. Added one line, `_test_project/vanlife-dashboard/`, and confirmed with git check-ignore that it actually took. Wrote the inner project's own gitignore too, venv, sqlite files, the proxy cache, the log file, all excluded from that side.

Wrote AGENTS.md and INSTRUCTIONS.md for this project next, modeled directly on the ones I already have for SEEKERS_GHOSTS. Same phase and step discipline, build then test then verify then commit then push then devlog, stop at the end of every phase and wait for me before continuing. INSTRUCTIONS.md ended up covering all thirteen phases I mapped out in planning, from this governance phase all the way through canvas boards, local AI tagging, transcription, and the DaVinci export at the end. Feels like a lot written out like that, but every phase is small on its own.

Then the actual repo. Confirmed with myself in chat before doing anything public facing, TheSeeker713/vanlife-dashboard, public, main branch. git init, first commit with the skeleton and governance docs, then `gh repo create` with push in the same command. Watched it land on GitHub, fetched it back down to make sure origin actually had what I thought it had. It did. Small relief every time that check comes back clean instead of surprising me.

Pushed the SEEKERS_GHOSTS gitignore change back to that repo too since it's routine, no separate approval needed for that one per my own rules there.

Good stopping point. Phase 0 is closed out, everything verified against real state instead of just trusting a green exit code. Next phase is the design and scaffolding pass, getting the actual window shell up with every panel placed before I start wiring real behavior into any of them. Looking forward to that one, it's the first time this project will actually look like something instead of just being folders and markdown.

### 20:27 - Phase 1 Steps 1.1-1.3: window shell, theme, menu bar, layout persistence

Got the actual window up today. First real UI, not just markdown and folder structure.

Started with the theme, one QSS file, light by default like I decided earlier when I walked back the dark-theme-first instinct. Dark is still coming, just not until the light one is solid and I've got something to toggle against. Built a small palette module too so the tag colors (keeper green, b-roll blue, reject red, audio-issue orange) live in one place instead of getting hardcoded all over the place later.

Then the shell itself. MainWindow with dock widgets for Browser, Timeline, Chat, Canvas, Metadata Viewer, and a Resource Monitor that stays hidden until someone asks for it. Player sits in the center since it's the main event once real footage shows up in Phase 4. Full menu bar too, File through Help, with most items disabled for now since their phases haven't landed yet. Kind of satisfying laying out a whole menu roster even though half of it does nothing yet, it's a map of where this thing is going.

Partway through, got a message asking if the chat, canvas, and the other right side panels could be expandable. Good instinct, and it fit naturally into what I was already building, so I added it right then instead of parking it for later. Each panel got a small header with a button that hides its siblings and gives that one panel the room, click again and everything comes back. Simple idea, took longer than it should have to get right.

That expand button chased me around for a good while, honestly. First pass, I couldn't find it in screenshots at all, kept second guessing whether it was even rendering. Turned out my layout wasn't pinning the header to the top like I assumed, no explicit stretch factors, so Qt was putting it wherever it felt like based on the placeholder content below fighting for space. Fixed that with explicit stretch factors and a fixed height on the header, and suddenly there it was, right where it should've been the whole time.

Along the way I also found a real problem, not just a cosmetic one. Clicking near a panel's title bar was hitting Qt's own native close button, which I hadn't realized was still active, and it just vanished the panel with no obvious way back short of digging into the View menu. Fixed the dock features so panels are movable and floatable but not closable that way anymore. Small thing, but the kind of small thing that would've been genuinely annoying to run into blind later.

Also spent a chunk of time chasing which tab shows up front by default in the grouped panels. Tried reordering the tabify calls, tried a raise_() after show, neither one stuck, and I was starting to think Qt was just being stubborn. Turned out to be stale QSettings from my own earlier test runs overriding whatever I did in code, not a real bug at all. Felt a little silly once I figured that out, but also relieved it wasn't some deep Qt quirk I'd have to work around forever. Cleared the settings, and after that, dock creation order does control which tab is frontmost, exactly like I expected in the first place.

Wrote a real persistence test too, not just eyeballing it. Resize the window, hide a panel, close it so the settings save, open a fresh instance, check the size and visibility came back. It did, first try once the rest of the bugs were sorted.

Phase 1 done. Everything committed, pushed, verified against the remote. Next up is the backend foundation, the database schema and the path allow-list and the actual wiring over to SEEKERS_GHOSTS's shared code. That one's less visual but it's the part everything else actually depends on.
