### 00:07 - Phase 2: backend and data foundation, and the package collision actually happened

First phase since I tightened up how a close actually works, so this is the real test of the new sequence, not just something written into a doc.

Started with config.py, the sys.path bridge over to SEEKERS_GHOSTS. Wrote the sentinel check, the three gates, felt good about it, wrote a quick test script to confirm GATE, TRANSCODE_GATE, and WHISPER_GATE were three distinct objects. Ran it. ModuleNotFoundError: No module named 'app.concurrency'.

Sat with that for a second because I'd literally written a whole paragraph in INSTRUCTIONS.md months ago telling myself this might happen. Turns out it wasn't a might. The moment my test script did `from app import config`, Python cached "app" in sys.modules as this project's own package, since that's what's on sys.path first when you run anything from this directory. By the time config.py runs its own sys.path.insert and tries `from app.concurrency import GATE`, it's too late, "app" already means the wrong thing and staying that way for the rest of the process. Renamed the whole package to vldash. Not a small change, eighteen files touched in the end between the actual rename and every doc reference to it, but the fallback was already agreed on before I ever wrote a line of code, so it was mostly just executing a decision I'd already made rather than making a new one under pressure.

Wrote a proper test for it this time instead of trusting a clean import: confirmed "app" now resolves to the sibling repo's real package (checked it has a concurrency submodule), confirmed "vldash" resolves to this project's own files, confirmed the three gates are genuinely three separate instances. All green. Also actually ran python -m vldash.main as a real launch, not just the import test, since a module that imports fine isn't the same thing as an entry point that boots.

db.py next. Twelve tables, all of it from the schema I'd already worked out on paper weeks ago, including the FTS5 virtual table for footage_search which I've never actually built before, had to look up the exact CREATE VIRTUAL TABLE syntax again. init_db() seeds the three default roots on first run and I made sure re-running it doesn't duplicate them, checked that by literally calling it twice in the same test and counting rows after each call.

paths.py, the allow-list choke point. Tested it against the real folders this time, not fixtures. J:\Studio 25 films\vanlife clip sort has four entries, Studio 25 Films has eight, SEEKERS_GHOSTS itself has twenty eight. Threw a `..\..\Windows` traversal at it and watched PathViolation fire correctly. Added an assert_writable() helper too, wasn't strictly required by the spec but it's a two-line function that directly enforces the household's own hard rule about readonly roots never being a write target, felt wrong to leave that purely as documentation when it's this cheap to actually check in code.

Health checks were the part I had to think hardest about testing properly. The spec wants both a healthy case and an unhealthy one, roots reachable and roots not reachable, and I was not about to rename J:\Studio 25 films\vanlife clip sort or D:\_Dev\AI-Setup\SEEKERS_GHOSTS just to prove an error path works. Those are real folders with real footage and a real repo in them. Inserted a fake root row instead, pointed at a path I made up that doesn't exist anywhere, ran the check against it, watched it correctly report unreachable, deleted the row after. Real roots never touched, error path still genuinely exercised.

Caught one small thing during the audit pass that had nothing to do with today's work: main_window.py had its own hand-rolled DATA_DIR constant instead of using the one now sitting in config.py, left over from before config.py existed. Small drift, the kind that's easy to miss and mildly annoying to find later once there are three copies of it instead of one. Fixed it while I was in there.

Launched the real app at the end, watched the status bar actually say "Ready. All startup checks passed." with my own eyes, not just in test output.

No UI/UX checklist for this one, nothing new for a person to click through, just the status bar line, and I already looked at that myself. Backend phase, backend verification. Feeling pretty good about the new close-out sequence holding up under an actual surprise instead of just the easy cases.
